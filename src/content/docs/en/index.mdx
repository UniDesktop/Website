## Why UDA

Shipping a cross-platform desktop app today means writing the same feature five times: `SystemParametersInfoW` on Windows, then `gsettings`, `qdbus`, `swww` and `hyprpaper` on Linux — each with its own failure modes, session assumptions, and no shared type system.

UDA replaces that fragmentation with one **capability-driven** Rust API: it probes the environment, picks the working backend, and degrades gracefully instead of panicking.

<CardGrid>
  <Card title="Portal-first" icon="rocket">
    Every Linux feature tries the XDG Desktop Portal before touching anything distro-specific.
  </Card>
  <Card title="Cascading fallback" icon="random">
    A strict tier chain: Portal → native DE IPC → CLI tools → a strongly typed `UdaError::Unsupported`.
  </Card>
  <Card title="Capability-driven" icon="magnifier">
    Features advertise `SupportLevel::Full` / `Restricted` / `Unsupported`, so your app can branch before it breaks.
  </Card>
  <Card title="Zero heavy dependencies" icon="puzzle">
    Pure Rust `zbus` on Linux, `windows-rs` on Windows. No Qt, no GTK, no bundled toolkit.
  </Card>
</CardGrid>

## Three entry points

| Entry point | Use it for |
|---|---|
| Rust crates | Native Rust apps — use the `AppearanceManager`, `TrayManager`, … traits directly |
| C-ABI (`include/uda.h`) | C/C++, or anywhere a stable ABI matters |
| Python / Node.js SDKs | `examples/python/uda.py` (ctypes) and `examples/nodejs/uda.js` (koffi) — no native build step |

## Shipped in v0.2.0

Light/dark appearance detection with live system-follow support · wallpaper management with fill modes, multi-monitor targeting and dark/light pairing · native notifications with icons, urgency and actions · keep-awake locks · **system tray** with a cross-platform menu model · **media control** with metadata read and playback commands · **session & power lifecycle** (lock, logout, suspend, hibernate, reboot, shutdown).

See the [platform support matrix](/en/reference/platform-support/).
